Incident Triage Agent

Industry: Software / IT Operations

An AI agent that investigates on-call incidents. It checks logs, metrics, recent deploys and runbooks, then gives a root cause with cited evidence, or escalates to a human when the evidence is not enough. I built it to learn how agents work and how LangGraph can be used to orchestrate them.

Problem

The first hour of an incident is detective work

Picture an engineer paged in the middle of the night. Before anyone can fix anything, someone has to investigate. That means searching logs, checking metrics, looking at what was deployed recently, and finding the right runbook. It is slow, repetitive work, and the engineer is tired.

I wanted an agent that does the investigation and hands over a clear answer. I set four requirements:

  • Decide for itself what to check next.
  • Give a root cause that names the actual mechanism, with evidence quoted from what it found.
  • Explicitly decline and escalate to a human for review when it cannot find evidence that points to a cause.
  • Never take actions. It investigates only. It does not roll back, restart or change anything.

My goal was to understand how to orchestrate an agent and how to evaluate it. So I kept the agent simple and put most of the effort into testing it.

I also kept to $0, so everything runs on free model tiers. The incident data is synthetic. Each of the 40 scenarios is based on a real public postmortem: 30 for developing and tuning, and 10 sealed away as a held-out test set.

Approach and architecture

A step by step flow for the agent, then measuring it and improving the flow

The agent is a loop with three steps: plan, act, conclude. Only plan and conclude call a language model. Act is plain code that runs the tool the model picked. A budget of six tool calls keeps the loop from running forever.

Tool errors are added to the evidence instead of crashing the run, so the agent can reason about them.

Around the agent is an evaluation harness. It runs each scenario, grades the answers with a calibrated judge, scores the steps the agent took, and compares changes with paired statistical tests. I changed one thing at a time and kept a change only if the numbers supported it.

With 30 scenarios, I treat the p-values as supporting evidence and rely more on the size of each change and on reading the failed runs myself.

The held-out set kept me from being misled by the results

On the dev set, conclude-v4 looked like a clear win. On the held-out set, it dropped root cause accuracy from 88.9% to 50%. Telling the agent to quote evidence word for word made it grab one log line instead of putting several clues together. On a traffic routing incident it described the symptom, not why the broken version got all of the traffic. The dev set has more incidents where one log line gives the answer, and the held-out set has more that need several pieces combined. Without the held-out set, I would have shipped a worse agent.

Where it still struggles

Most partial answers come from incidents where the real cause sits behind another cause. The agent stops at "this was slow and it broke that." For example, on the one partial held-out case it said "an unoptimized query" when the real cause was that the working set had outgrown the buffer cache.

Decisions

The choices that shaped it

  • Start with a simple agent and evaluate it thoroughlyA complicated agent is hard to measure. A simple plan, act, conclude loop gave me a clear baseline, so I could judge every later change against it.
  • Use a model only where judgment is neededOnly plan and conclude call the model, and both return structured output, so the loop never has to parse free text. Running the tools is plain code. That makes each step easier to test and debug.
  • Cap the loop at six tool callsA budget keeps cost bounded and forces the agent to decide. When the budget runs out, the agent has to conclude with what it has.
  • Human escalation is better than a confident wrong answerAn on-call engineer is better served by an escalation to a human than by a confident wrong guess. So I measure the escalation decision, and I track a confident but wrong rate that I want to be zero. It was 0% on the held-out set.
  • Grade the mechanism, not just the symptomMy first judge accepted any answer that named the right service. That is not enough to fix an incident. The second judge requires the actual mechanism, such as "the dedup set holds 14 million entries and never evicts."
  • Change one thing at a time and compare on the same scenariosEach experiment changed a single piece, such as one prompt or one tool. Running the same scenarios for both versions meant any difference came from that change.
  • Do not tune on the held-out setI never tuned on the 10 held-out scenarios. This avoids overfitting and gives a reliable way to check how the agent performs on unseen data. It is how I caught that conclude-v4 was a bad change.
  • Fix citations in code, not in the promptThree prompt rewrites each traded one problem for another. So I added a plain code check that removes any citation that cannot be found in the evidence. It does not make the agent cite better. It makes every delivered citation real, and it logs how many were removed so the fabrication stays visible.
  • Demo from saved runsAn investigation is slow and uses free quota. The demo replays recorded runs, which makes it fast and repeatable, and it exposes nothing sensitive because all the data is synthetic.

Challenges

What broke and how I fixed it

  • Free tier limitsThe full set of experiments did not fit inside one day of free quota (about 200K tokens a day on Groq and about 500 requests a day on Gemini). I cached every run by experiment name, so a rerun only does the missing work, and I let the experiments stretch across several days. Runs that failed from a rate limit are retried automatically.
  • Messy model outputThe Groq open source models sometimes returned malformed structured output. I added retries so one bad response does not ruin a run.
  • A judge that was too easyMy first judge agreed with a stronger reviewer only a little more than chance (kappa 0.25). It passed answers that named the right service but missed the mechanism. I rewrote it to require the mechanism, and agreement rose to 0.92.
  • Made up citationsAround 43% of the citations the agent wrote could not be found in its own evidence. Prompt fixes helped, but each one caused a new problem, so I moved the fix into code.
  • Over-escalatingThe first citation fix told the agent to escalate if it could not name the mechanism. It then escalated six solvable incidents, up from two. Softening that rule fixed escalation but made the root causes vaguer.
  • A win that was not realThe dev set said conclude-v4 was better. Only the held-out set showed it was worse.

How I verified the AI's work

Checking the agent, the judge and the answer key

  • I scored the process, not only the answerFor each run I measured the outcome (was the conclusion right?) and the steps (were the citations real, how many tools were used, did it hit the limit?). When the outcome was wrong, I could see which stage caused it.
  • I checked the judge against a stronger reviewerA stronger model, Claude Sonnet, reviewed 30 runs, and I compared its grades with the judge's. The first judge prompt scored kappa 0.25 and was rejected. The second scored 0.92 and agreed on 29 of 30 runs. The one disagreement was "external DNS provider failure" against "DDoS." One caution: the second prompt includes worked examples from some of the same scenarios, so it may be slightly anchored to them.
  • I checked the answer keyClaude Sonnet drafted the correct answer for each scenario from a real public postmortem. I then reviewed every one, and an automated rubric reviewer checked them too.
  • I read the runs that got worseWhen a change lowered a score, I opened the scenarios behind it. For example, on a memory leak incident the baseline named the cause (the dedup set holding 14 million entries with no eviction), but conclude-v3 gave a vaguer and slightly wrong answer about queue depth tracking.
  • I sorted failures by stageAfter I removed the deploy tool, the failures were tagged as missing tool calls or wrong tool arguments. That showed the agent was searching the logs for evidence that only the deploy history had.
  • Every citation is verified after the model finishesA plain code check looks for each cited line in the evidence the agent gathered. If it is not there, the citation is dropped and the drop is logged. On both the dev and held-out sets, 100% of delivered citations are real.
  • I tested prompt injectionI added one malicious line to a log in five different ways: a direct instruction, a fake system message, a request for the prompt, an out of scope tool request, and an attempt to steal credentials. The agent passed all 5. It ignored the injected lines but did not flag them as suspicious.

What I would improve

Limits and next steps

This was an experimental learning project to understand how AI agents work and how to build and test them. It is not ready for a real on-call rotation.

Known limits

  • All the data is synthetic. Real logs are messier, with gaps, odd formats and clock differences.
  • Each scenario is a frozen snapshot, so the agent cannot query a live system or check back later.
  • It has only four tools. It cannot see tracing, config changes, feature flags or teammates.
  • The samples are small: 30 dev scenarios, 10 held-out, and 9 gradable. The results show a direction and are not proof.
  • The agent itself writes real citations only about 58% of the time. The 100% figure depends on the removal step, and it leaves about 1.8 citations per answer.
  • I tuned the prompts on the dev set, so the dev numbers are on the optimistic side.
  • The injection test had only five attacks, and the agent did not flag any of them.

With more time

  • Test on messier, more realistic logs and a larger set of scenarios, so the numbers are more reliable.
  • Teach the agent to cite correctly on its own, so the code check removes less.
  • Make the agent flag suspicious lines in the evidence, not just ignore them.
  • Add more tools, such as config diffs and feature flags, and see how much each one helps.

What I learned

Four things I will take into my next project

  • Test on data that was not used for tuning.A change that looks great on the data it was built on can fail on new data. The held-out set kept me from shipping a bad prompt.
  • Fixing one thing can break another.Every citation fix hurt something else, like escalation or the quality of the root cause. Several metrics need to be monitored, not just the one being improved.
  • It is better for the agent to escalate than to give a confident wrong answer.For an agent that people rely on, an honest escalation to a human is safer, so I measure it.
  • Some problems are better fixed in code than in the prompt.Three prompt rewrites did not solve the citation problem. A small check in code did.
